## 1. 一句话判断

**阶段**：这是一个能跑的实时打杆叠层原型，不是"可开始验收版本"。对照试点最小验收清单（L154-159）：第 1、2 项代码已覆盖；第 3 项做到一半（能导出，但没有选手代号、没有 `parseTrainingSession()`，"重新解析"目前只有测试里一行 `JSON.parse`）；第 4、5、6 项代码贡献为 0，全部要靠人工台账。

**最大风险**：试点的核心指标"≥80% 训练尝试形成有效 Session"（L182）会被三个工程缺陷直接吃掉——Session 单槽内存、刷新/覆盖即丢（`hooks/use-training-session.ts:36/:53`）；没有选手代号与有效性判定（`lib/training-session.ts:32-51`，L156/L168）；断线与演示状态静默录废（`hooks/use-betaflight-telemetry.ts:156/:191-198/:224-233`，`components/flight-dashboard.tsx:194`）。第二个风险是成功标准"周复盘 5 小时 → 2 小时"（L181）在产品里零机制：教练拿到的是一条 20 Hz 曲线，仍要从头拖 DVR，老板付 ¥6,000 前问"我省了几小时"，答案是 0。

**接下来 2 周最该做的一件事**：在试点起算日之前发布"可开始验收版本"——Session 持久化 + 选手代号/schema v2 + 有效性判定与连接看门狗 + 最小埋点（19 个 Phase 1 事件名、约 1.5 天）。埋点是创始人的第一优先级，也应该做，但它的作用是**证明和归因**（验收第 5 项的分母、第 6 项的"可复现记录"），不提升任何一个验收数字，所以按最小版本做，不按分析平台做。

## 2. 代码库现状体检

只保留事实核查为 confirmed / partially 的问题；partially 的已用核查员给出的正确位置。跨视角重复的问题已合并为一条，"视角"列出所有提出者。

### Critical

**C1. Session 只有一个内存槽位：开下一包前忘了导出、误刷新、Chrome 崩溃，上一条永久丢失**
证据：`hooks/use-training-session.ts:36` 单个 `lastSession`，`:37` 草稿只在 `useRef`，`:53` 直接覆盖；`components/flight-dashboard.tsx:403` 文案"记录保存在浏览器内存"、`:404-406` 导出按钮只对最后一条；`README.md:45` 把风险写在文档而不是界面；全仓库无 `beforeunload` / IndexedDB。
影响：一天 15 包电，忘一次导出就是 L182 分母里的一次失败，而且事后无法证明它存在过。
修法：IndexedDB 每 5 秒落草稿、结束即写入；页面下方"今日记录"列表（选手 / 时长 / 有效 / 已导出）；`beforeunload` 有未导出记录时拦截；"结束即自动下载"开关。
视角：ceo / analytics-events / coach / frontend / security-privacy / ux / data-eng

**C2. 数据模型没有选手、俱乐部、工作站、版本、备注，文件名是 UTC 时间 + 8 位乱码，没有解析函数**
证据：`lib/training-session.ts:32-51` 字段只有 id/startedAt/endedAt/durationMs/initialSource/dataSources/sampleCount/estimatedRcSampleRateHz/timing/video/samples；`:141-145` 文件名 `fpv-session-<UTC>-<8位id>.json`；grep `athlete|clubId|选手` 零命中；`lib/training-session.test.ts:63` 是全仓库唯一的 `JSON.parse`。
影响：验收第 3 项"文件能够重新解析，并在试点台账中关联到选手代号"只能靠纸台账对时间戳，一天 15 条必错；错一条，"可见的训练趋势"（L59）就是假的。
修法：`schemaVersion: 2` 新增 `athleteCode`、`notes`、`workstationId`、`build`、`channelsUs`、`markers[]`；开始记录前选代号（最近 10 个可点）；带校验的 `parseTrainingSession()` 兼容 v1；文件名改为本地时间 + 代号。
视角：ceo / coach / ux / security-privacy / data-eng

**C3. "有效训练 Session"（L168）没有代码实现：演示模式可录、录制中可"返回演示"混入、导出不带来源**
证据：`hooks/use-training-session.ts:39-46` `startRecording` 不看 `source`；`components/flight-dashboard.tsx:194` 记录按钮无条件可点、`:198-200` "返回演示"在录制中始终可点；`hooks/use-betaflight-telemetry.ts:118-121` `useDemo` 不检查录制；`lib/training-session.ts:109-135` 无 validity、`:122` `dataSources` 可变成 `[ground_rc, demo]`、`:144` 文件名无来源标记。
影响：教练现场不知道这条算不算数；演示/混合数据混入台账，L168 明确"演示数据……不计入"。
修法：`assessTrainingSession()` 纯函数返回 `{ valid, reasons[] }`（`source_not_ground_rc / mixed_sources / too_short / too_few_unique_samples / non_monotonic / no_athlete_code / interrupted`），写入 JSON 并在 session-card 显示；`connection !== "live"` 禁止开始记录；录制中禁用"返回演示"；demo 文件名前缀 `demo-`。
视角：ceo / analytics-events / coach / ux / data-eng

**C4. `source` 与 `connection` 混用：取消/失败后冻结在假在线状态，"数据桥在线"永不回退，断线后 REC 计时照跑**
证据：`hooks/use-betaflight-telemetry.ts:191-195` 在 `:198 requestPort()` 之前就 `disconnect()`（停掉演示定时器）并 `setSource("serial")`；`:229-233` 取消/失败只置 error 不恢复演示；`:156` 每帧 `setConnection("live")` 且无处回退；`:193` connecting 无超时；`:207-222` 写失败不清 `pollTimer`；`:224-228` 读失败不停记录；`components/flight-dashboard.tsx:154/:186/:281-282/:354/:356-360` 所有在线标签（GROUND_RC / MSP LIVE / 三格点亮）只看 `source`；`hooks/use-training-session.ts:68-75` 计时器只看 `isRecording`；`lib/web-serial.d.ts:1-14` 未声明 `disconnect` 事件与 `getInfo()`。
影响：USB 被踢、选错串口、误点取消弹窗——训练日最常见的三件事——都表现为"看起来在录其实没录"；同时误导验收第 2 项"数据来源不是演示模式"的判断。

视角：analytics-events / coach / frontend / ux / embedded / data-eng / ceo

**C5. "周复盘 5 小时 → 2 小时"（L181）在产品里零机制**
证据：`lib/training-session.ts:7-22` 样本只有 `elapsedMs` 和打杆值，没有任何 Marker / 墙上时钟标注；`components/flight-dashboard.tsx` 全文无"标记"按钮；`docs/hardware-architecture.md:47` 把时间标定排在开发阶段第 4 步。

视角：ceo / coach

### High

**H1. 样本采集挂在 React 渲染周期上：同一 USB chunk 多帧只记最后一帧；后台标签页被节流到 1 Hz；无 gap 统计**

视角：frontend / embedded / coach / analytics-events / data-eng

**H2. 错误是自由字符串：3 处英文 DOMException 直出、无错误码、横幅只显示一条且不可关闭**

**H3. AUX/ARM 通道与 roll/pitch/yaw 原始 µs 在解码阶段丢弃，clamp 截断 ELRS 端点；MSP.MOTOR 分支是死代码**

## 3. 埋点统计方案

### 3.1 要回答的业务问题

这是一个单页、约 14 个按钮、一家俱乐部两台工作站的产品。"哪一页流失多"要改问"6 步漏斗死在哪一步"；"哪个按键没人点"只需盯 5 个按钮（开始记录、导出、返回演示、简洁模式、重置叠层）。埋点要回答：

1. **验收第 5 项的分子分母**：本周有多少次"点击开始记录"的尝试（含失败的）？其中多少条按 L168 有效？多少条被导出？——覆盖率是否 ≥80%。
2. **白录了多少**：多少 Session 因为覆盖、刷新、录制中关页而丢失（`session_lost`）？这是"流失"的直接度量。
3. **连接失败主因**：串口失败是取消弹窗、串口被占、选错端口还是 USB 掉线？画面失败是选错设备、权限还是被 OBS/DVR 软件占用？——决定第 2–5 天修什么。
4. **静默劣化**：录制中出现了多少次数据冻结（`telemetry_stalled`）、标签页被切走多久（`page_hidden`）、遥控器失联多少次？——解释"为什么这条无效"。
5. **有效使用时长**：一次打开页面，画面 + 飞控同时在线的时间占多少？演示模式占多少？
6. **环境噪声**：多少次打开来自根本不可能成功的环境（微信内置浏览器、Safari、HTTP、视口 <1120px）？
7. **这周俱乐部到底打开没有**：决定要不要打电话。
8. **验收第 6 项的可复现记录**：任何一次故障都要能给出 `error_code + build + 时间戳 + 当时状态`。

### 3.2 工具选型结论与理由

**结论：自建最小管道，不引入第三方分析 SDK。** `lib/analytics.ts`（localStorage 队列 + `fetch keepalive` / `sendBeacon`）→ Vercel 上的同域 `app/api/events/route.ts` 处理入口 → 新建的独立 FPVHelper Supabase 托管 `app_events`。分析写入只读取 `FPVHELPER_ANALYTICS_SUPABASE_URL` 与 `FPVHELPER_ANALYTICS_SUPABASE_SECRET_KEY` 两个服务端配置，不回退到公开、通用或旧 `service_role` 变量。试点期不做看板产品。

理由：
- **规模**：试点是 1 家俱乐部、2 台工作站、4 周约 16–30 条 Session、几十次页面打开，任何转化率都没有统计意义；埋点的价值在于"每一次失败都能归因"，而不是漏斗曲线。
- **数据边界**：Vercel 是请求处理入口，独立 FPVHelper Supabase 是境外托管端；两者的角色、平台日志和保留期都必须写入数据附件。不引入第三方 analytics SDK，但这不等于数据不出境。
- **可迁移但不双写**：事件信封保持通用 `event_name` + `props` 结构；当前禁止第三方 analytics SDK 和 PostHog 双写。任何未来接收方变更都需新的书面数据附件与工程审批。
- **与训练数据同源**：`recording_id` 贯穿 `app_events` 与未来的 `training_sessions`，验收指标可以一条 SQL 算出来（data-eng 视角）。

**中国网络考量**（必须写进实施前置）：
1. 浏览器请求同域 Vercel 入口，减少客户端直连境外 Supabase 的依赖；这不保证中国大陆网络可达性或延迟，D7 前必须用俱乐部真实网络和手机热点实测并记录。
2. 赛道网络不稳定（L48）而产品核心完全离线可用，所以埋点必须离线容忍：localStorage 队列（上限 500 条、7 天过期）、`online` 事件与每 10 秒 flush/retry、`pagehide` 用 `sendBeacon`；上线前在 DevTools 断网 → 操作 → 恢复验证补发。
3. 工作站系统时间可能不准：服务端记 `received_at`，看板以 `received_at` 校正。
4. 两个 origin 会把同一台工作站算成两台：生产统计只接受 `race.fpvsuperapp.com`，`helper.longxl.com` 强制标为内部非生产并排除；当前不做重定向（H5）。
5. 数据出境：Phase 1 的随机 `workstation_id` + 枚举属性仍属于假名化数据；是否构成个人信息、需要何种告知/同意/跨境程序，交由有权法律/合规负责人结合真实 Vercel 与 Supabase 配置书面判断。
6. 开发/预览流量会污染只有一家俱乐部的数据：`VERCEL_ENV === "production"` 才发送，`hostname / vercel_env` 作为公共字段兜底过滤。
7. Supabase 项目的暂停/恢复、区域、备份与配额取决于实际项目和当时方案，本文不作云端事实声明；实施时从项目真相面与服务商文档核验。客户端对 5xx 退避重试，是否需要 keep-alive 或升级方案必须另行审批。

**规范**：
- 属性值只允许枚举、数字、布尔、哈希；`props` < 4 KB；在 `lib/analytics/events.ts` 用 TypeScript 联合类型把每个事件的属性写死，非法属性编译不过。
- 错误一律先经 `lib/analytics/error-codes.ts` 映射为枚举（`DOMException.name + message` 正则），UI 中文文案与埋点共用同一张表。

- "真实数据"一律以 `connection === "live"` 判定，不以 `source === "serial"` 判定（C4）。

### 3.7 隐私与合规规则

1. **假名化 ID**：`workstation_id` 是随机 UUID，不含机器名/序列号/MAC/指纹，但可由团队线下台账重新关联，因此不得称为匿名；映射永远不写进事件表或可 join 的外键。
2. **不采姓名**：任何时候不采集姓名、手机、邮箱、原始 UA、`device.label`、串口名、`error.message` 原文、Binding phrase（`docs/hardware-architecture.md:56`）、20 Hz 打杆样本、视频帧、串口原始字节。`error_message` 只保留分类枚举；设备只保留 `device_kind` 与 USB VID/PID。
3. **选手代号**：Phase 1 事件设计上不含姓名或选手代号；这不替代对假名化工作站数据、平台日志及未成年人场景的法律判断。Phase 2 若引入 `athlete_code_hash`，前端只接收“已取得监护人同意的代号列表”（L113），未同意代号不得出现在任何事件或云端摘要里。
4. **未成年人与出境**：是否构成敏感个人信息、需要何种 PIA/跨境机制与平台日志保留，应由有权法律/合规负责人结合主体和地区书面判断；本文不提供法律结论。选手档案上云前必须另行审查。Route Handler 不主动落 IP/UA，平台日志边界仍需实测并写入附件。
5. **报价单附件必须写的一行**（L112 要求“采集字段、用途、处理方/托管方、访问人、保留期、删除方式”）：“假名化产品使用统计：操作事件、设备环境类别、分类错误码、Session 时长与样本数统计；不含画面、原始 RC、选手代号或原始错误文本；经 Vercel 同域入口处理后写入境外托管的独立 FPVHelper Supabase；平台日志边界、访问人、保留期和删除方式以最终书面附件为准；工作站可关闭统计。”书面确认、云端和工程验收完成前保持关闭；具体关闭机制须由工程实现与验收确认。
6. **界面与文档同步**：文案改为"视频与原始 RC 不上传；假名化使用统计在书面确认后可启用并可关闭"；README 增加「离开本机的数据」表，`hardware-architecture.md` 引用该表，同一口径复制进附件。
7. **保留与删除**：`app_events` 90 天（覆盖 4 周试点 + 复盘）；试点结束 30 天内俱乐部未转年许可则删除该 `workstation_id` 全部事件（一条 SQL）；聚合后的周报数字不含标识可长期保留；本地离线队列上限 500 条、7 天过期。
8. **工程约束**：不引入第三方分析 SDK 写进 `CLAUDE.md`；`VERCEL_ENV !== "production"` 不上报；Route Handler 必须校验受控 ingest token、严格事件/属性白名单、批量/体积/时间窗、幂等与限速；Vercel Preview 访问保护需按实际项目与方案单独核验。
9. **JSON 文件里的代号**：Session JSON 内含 `athleteCode` 与 `notes` 后属于假名化数据，README 注明"请按俱乐部内部规则保管"；`consentRef`（监护人同意单编号）留在台账不进文件。

### 3.9 现有代码中妨碍埋点的地方及先改什么

按顺序改，前 4 项是埋点上线的硬前提：

1. **错误是自由字符串**（`use-betaflight-telemetry.ts:32/:227/:232`、`use-video-capture.ts:69`）→ 先做 `error-codes.ts`，否则 `reason` 字段没有来源。
2. **`source` 在 `requestPort` 前就切 serial**（`:191-198`）→ 先分离 `source / connection`，否则"真实数据时长"把取消后的冻结时间算进去，`recording_started.connection_at_start` 也无意义。
3. **没有 `build` 号**（`package.json:3` 未引用，`next.config.ts` 无 env）→ 注入 `NEXT_PUBLIC_APP_VERSION`，否则任何事件都无法按发布切片。
4. **没有有效性函数**（`lib/training-session.ts:109-135`）→ `assessTrainingSession()` 是 `recording_stopped.valid`、`session_lost.valid`、`page_unloaded.unexported_is_valid` 三个字段的唯一来源。
5. **没有看门狗**（`:156` 永不回退）→ `telemetry_stalled` 与 `serial_connect_result(first_frame_timeout)` 需要它。
6. **解析器无计数器**（`lib/telemetry.ts:93-95`、hook `:177`）→ 两个 ref 计数器，一行改动 + 一个测试。
7. **`web-serial.d.ts` 缺 `getInfo / disconnect`** → 否则拿不到 VID/PID，拔线只能等写入失败。
8. **10 个 onClick 全是内联闭包**（`flight-dashboard.tsx:194/199/201/235/237/243/251/257/262/405`），按钮文案随状态切换（`:196`、`:244`）→ 只把 5 个关键按钮抽成具名 handler；其余在 hook 状态迁移点埋，不碰。
9. **StrictMode 双 mount**（`next.config.ts:4`）→ `app_opened` 用 ref 守卫。
10. **叠层每帧写 localStorage**（`draggable-stick-overlay.tsx:159-165`、`:126-134`）→ 绝不在 `storeStickOverlayLayout` 埋点，Phase 2 只在 `endInteraction` 比较起止布局。
11. **两个域名（已拍板）**→ 只允许 `race.fpvsuperapp.com` 产生生产统计；`helper.longxl.com` 是内部验证且强制非生产。当前不重定向，未来停用内部入口时再审批 308。

## 6. 各视角的关键洞察

**CEO / 创业顾问**：护城河不在实时叠层（Betaflight OSD 自带 stick overlay，Blackbox 也能叠视频），而在"按选手归档、跨周可比、教练可标注"的俱乐部数据工作流。埋点方向对，但框架要换：单页产品 6 个月内没有"哪一页流失多"的统计意义，值钱的是把验收第 5 项和成功标准的分母变成自动采集的事件。路线：持久化 → 选手代号 → 有效性判定 → ARM 切段 → 指标库 → 复盘清单 → 周报 → 云端摘要；账号系统与视觉计圈继续往后放。

**产品数据分析师（analytics-events）**：16 条问题全部被核查确认、行号无一错误，是最可照抄的 tracking plan。核心主张：埋点要按"6 步关键动作漏斗"而非页面定义；`serial_connect_succeeded` 必须以首帧 MSP_RC 为准而不是点击；`session_discarded`（未导出就关页）是最重要的流失信号；错误必须先变成枚举，否则每条失败都是不同的英文句子。与 security 的分歧在工具：主推 PostHog Cloud + 反代，本方案采纳其事件设计、否决其接收方。

**FPV 教练 / 俱乐部老板**："今天它省不了我一分钟复盘时间，¥6,666 我不会付；但离能付并不远：选手/包数标签 + 停止即出小结、一个'标记这段有问题'的键、当天记录不丢，我就愿意谈。"他指出 8 份分析里只有他和嵌入式工程师看到的现场最大风险：地面接收机一次只认一台遥控器，5 个选手 5 台遥控器怎么换人，文档和界面都没交代。与设计师的微妙分歧：ux 要把 RSSI Gauge 删掉，教练说那是唯一对他有用的信号——"对频了没"——只是被包装成"legacy RSSI 非机上 LQ"他认不出；本方案取教练的用法：删 Gauge，把它变成"遥控器：已连接 / 等待连接"的大状态。

**前端工程师**：找到了别人没看到的真实 bug——同一 USB chunk 多帧被 React 批处理吞掉、trail dot 用 index 做 key 每帧重建 DOM、拔线后无 teardown；并给出正确的工程立场：埋点插在 hooks 的状态迁移点而不是按钮上，`source`（意图）与 `connection`（链路）必须分开。与 analytics/ux "每个按钮显式 track + data-track-id"并不冲突，本方案两者并用但只给 5 个按钮加标识。

**安全与隐私工程师（历史分析，已勘误）**：埋点是产品第一次让数据离开本机。随机工作站 ID 属于假名化而非匿名；是否需要出境评估必须由有权负责人判断。实施决定为 `race.fpvsuperapp.com` 客户入口、`helper.longxl.com` 内部非生产、独立 FPVHelper Supabase，且书面确认前关闭统计。

**产品设计师**：把自己放在训练场地里——强光或昏暗、手里拿着遥控器、离屏幕 2–3 米——得出"这是一块为开发者调试设计的控制室面板"：同一油门显示 5 遍、来源标签 11 处、33/53 处字号 ≤10px，而真正需要放大的 REC 计时和油门 % 反而最小；最大的实时数字给了 README 自己说不代表飞行器的地面桥电压。首屏默认跑演示且演示标识在 ≤1120px 时整条消失，是第一天就会误判验收第 1、2 项的陷阱。

**嵌入式 / ELRS 工程师**：协议层解码正确（脚本实测），但 20 Hz 轮询（Nyquist 10 Hz）不足以支撑"平滑度 / 抖动 / 快速修正"类指标，failsafe 值会被当作"油门 0%、摇杆回中"写进有效 Session，一个坏字节会连丢 6–7 帧。最大的分歧点：主张 Gamepad/WebHID 直读 EdgeTX 遥控器（250 Hz 级、零硬件、零绑定）取代第二接收机 + 桥接飞控，而现有路线图、验收清单 L155 和 coach 的换人担忧都建立在 MSP 桥接之上——本方案把它定为许可后的 v2 数据源评估，但承认它是换人重绑问题的技术解。他唯一的误读是"顶栏写死 RATE 20 HZ"（`flight-dashboard.tsx:186` 只在演示模式显示 20 HZ）。

**数据工程师**：实测了 JSON 体积（4 分钟 1.87 MB → 列式 gzip 27 KB），给出了最完整的 schema / RLS / 摄入 / 保留删除草案，以及 12 个指标的定义和"20 Hz 下哪些只能做同选手趋势"的标注——这是周报能承诺什么的依据。与 security 在 Supabase 上的分歧（共用项目里建独立 schema 还是新建项目），本方案取 security：新建项目，因为它同时满足你的全局规则。

**三份审查的声音**：事实核查 107 条零 refuted，说明 8 个视角在核心事实上高度一致且全部被代码证实。商业聚焦审查把 70 余条建议分成四桶，结论是"这个产品离可开始验收版本差的不是埋点，而是三件会直接扣 80% 覆盖率和 ¥6,000 的事"；埋点按 1.5 天最小版做。完整性审查指出 8 位 agent 的共同盲区：全部把解法落在"改代码"上，没有人利用"只有 2 台受控工作站"去用 Chrome 企业策略零代码解决权限弹窗和后台节流，也没人讨论分发形态、微信/国产浏览器、发布纪律、许可证、SaaS 套餐条款、ICP、销售演示资产和试点前的 DVR 基线周——这些非功能项已并入第 4 章。

## 7. 需要创始人回答的问题

按对决策的影响排序：

1. **已决定，待真机量时**：每位选手一套预绑定的独立 Bridge FC + RX；仍需在真实场地测量换套件耗时和链路影响。
2. **已决定，待云端核验**：产品名 FPVHelper 训练工作台；客户入口 `race.fpvsuperapp.com`，`helper.longxl.com` 仅内部非生产；当前不做重定向。
3. **已决定，待创建/核验**：新建独立 FPVHelper Supabase；区域、RLS、migration 执行和 Vercel 连接仍需云端证据。
4. **已决定，待书面确认**：假名化统计经 Vercel 到境外独立 Supabase；书面确认、关闭机制和工程验收前保持关闭。
5. **老板愿意贴在墙上的 3 个数字是什么？教练每周 5 小时 DVR 具体在找什么**（炸机前操作、过门线路、油门控制）？这决定指标 v1 冻结哪 3 个、复盘清单自动挑"时刻"的规则怎么写——写进第一份周报后就不能随便改口径。
6. **试点起算日、DVR 基线周（T-10 至 T-3）和收款主体 / 发票类型**分别定了吗？基线周必须在起算日之前完成否则 L181 没有对照；收款主体是个人还是大陆公司决定 ICP / 国内云这条线是否存在。
7. **现场设备**：工作站是 Windows 还是 macOS、Chrome/Edge 版本、屏幕是笔记本 / 显示器 / 投影、教练离屏幕几米；采集卡与桥接飞控具体型号；DVR 是 DJI / Walksnail / HDZero / 模拟，录像文件名带不带本地时间；训练时是否同时开 DVR 软件或计时器窗口（决定后台节流的严重程度）。
8. **谁按"开始记录"、Session 粒度是一包电还是整段训练、选手代号名单谁维护**？是否允许把代号写进 JSON 与文件名？未成年选手比例多少、监护人书面同意由俱乐部收还是我们出模板？
9. **桥接飞控是否允许一次性 CLI 配置**（`serial_update_rate_hz`、`rxfail` 哨兵值）以支持 50 Hz 轮询？如果允许，README 与安全边界的"不写入 Betaflight 配置"需改为"不写入飞行器飞控"——这决定平滑度类指标能否写进报价单。
10. **演示模式在试点版本里还要不要存在？** 藏到 `?demo=1` 后面让工作站永远不会误进；演示下的"开始记录"直接禁用，还是只弹确认并打 `demo-` 标记（影响 L182 分母的口径）。
