# 打杆实时监看中的过门计时

实时计时位于“工作站设置 → 实验功能 → 实时过门实验”，首次打开才加载面板并读取本机视觉记录。它复用当前选手的取景和[视觉实验台](vision-lab.md)中的门档案，无须先录成文件；每次分析一个起终点门、一路选手画面。日常飞行工作台保留画面、打杆叠层与录制，详细遥控数据按需展开。

当前版本生成待人工确认的穿越候选。确认两次穿越才形成第一圈，有待复核事件或观察缺口的区间不纳入最快已复核圈。单门无法验证完整赛道，也无法仅凭相似外观保证正向穿越。

## 开始使用

1. 打开视频输入，选择当前选手并确认姓名。四合一输入先通过“裁切与绑定”选择该选手的区域，实时计时复用这个取景。
2. 从“工作站设置 → 实验功能”打开“实时过门实验”，选择本机门档案。没有档案时展开“配置新的计时门”，截取当前取景或导入 10 MB 内的 PNG/JPEG/WebP 照片，框选门框、填写名称，再点“保存并绑定计时门”。录像实验台的门档案可直接共用或导入。
3. 如需同时保存视频与打杆数据，先用原来的“开始记录”开启训练录制，再点“开始过门计时”。本轮将记录真实训练 Session ID，但不宣称时间同步。仅观察画面也可独立开始计时。
4. 首次开始会根据本机能力下载固定的 GPU FP16 权重（约 44.4 MB）或 CPU q8 权重（约 24.5 MB），以及运行库。GPU 初始化失败时回退 CPU。门照片和视频画面留在本机，未点击开始不会加载模型。模型准备期间计为观察缺口。
5. 查看待确认的穿越，填写理由后确认、排除或改时刻。现场观察到穿越时，可填写人工理由并点击“人工确认一次穿越”；采用点击时的主机时间，仍包含人工反应延迟。
6. 停止过门计时后继续查看、复核和导出。停止只释放识别使用的 Worker 和借用的视频元素，原视频流与训练录制由原来的按钮控制。

切换选手、视频源、裁切、门档案或训练记录会结束本轮，避免混合来源。离开实时过门实验页会取消模型准备或中断识别并保存已有结果，原视频与打杆录制继续；返回实验页保留复核状态，不自动恢复识别。浏览器标签页转入后台、视频断开或超过 2.5 秒没有新帧也会中断。每轮最多 30 分钟，之后需明确开始下一轮。

## 保存、复盘与分享

独立 IndexedDB 数据库 `fpvhelper-live-vision` 保存记录，门档案仍在 `fpvhelper-vision-lab`。不修改原训练数据 schema，不把视频编码进 JSON。视频仍按原流程另存 MP4 或浏览器支持的 WebM，并保留打杆 OSD；本版本计时数字显示在网页面板中，尚未烧入录像。

| 内容 | 保存方式 |
| --- | --- |
| 来源 | 视频源 ID、选手 ID/姓名、流与轨道 ID、尺寸、归一化裁切范围、可选训练 Session ID |
| 门与模型 | 档案 ID/修订/图像哈希/参考选区，固定模型 ID、revision、实际所用权重来源哈希和 WebGPU / WASM 后端 |
| 时间 | `host_presentation_estimate`，主机单调时钟与时间原点；可用时附视频回调的媒体位置、帧序号和呈现时间 |
| 原始观察 | 已处理新帧时间、取景/往返/预处理/模型/匹配耗时、阈值前最佳框与余弦分数、待复核候选及其证据区间 |
| 修正 | 追加式人工确认、排除、改时刻、补记和理由；保留原始候选 |
| 缺口 | 模型准备、帧回调跳跃、推理覆盖不足、中断尾段；不补造连续数据 |

约每 5 秒暂存一次（不阻塞推理、不积压检查点），复核和正常停止也保存。重开页面可从“恢复本机计时记录”读取历史；未正常结束的旧记录标为中断，未知结束时间保持未知，不自动恢复识别。

JSON 保存完整档案（导入上限 64 MiB，30 FPS / 30 分钟最多 54,001 次观察），CSV 提供圈速表；每次导出使用新的唯一文件名。下载发起不等于磁盘写入完成，请确认浏览器下载结果。保存失败时保留当前页结果供重试或导出；只有重试保存成功，或用户明确点击确认当前 JSON 下载完成后，才能切换记录或开始下一轮。多标签页保存拒绝覆盖不同的原始观察或复核历史。浏览器清理站点数据会清除本地库，原视频和导出的档案需要自行备份。

## 性能与验证范围

实时识别自动选择 WebGPU FP16；浏览器没有支持半精度的 GPU 或 GPU 初始化失败时，回退单线程 WASM q8，并显示原因。实际后端与权重来源随记录保存；推理期间失败会停止本轮，不会混合更换模型。录像实验台仍默认使用 q8。

默认分析上限为 30 FPS，可在开始前选 15 FPS。取样只接受最新呈现帧，每次只有一个推理任务，忙碌时跳过而不积压。实际速度取决于输入和本机负载，应以面板的完成分析 FPS 为准；界面最多约每 250 ms 更新，检查点按时间暂存。串口 100 Hz 采集目标和 20 Hz 历史更新逻辑保持不变。

展开“查看匹配画面与分析原因”，可以看到实际送入模型的裁切画面、阈值前最佳匹配框、分数、各阶段耗时、未分析帧计数、匹配帧数和轨迹拒绝原因。黄框低于匹配阈值，绿框达到阈值；相似度不是穿门概率。静止的门没有接近和离场过程，不能单凭匹配计圈。

新轨迹规则与目标 FPS 分开：超过 1500 ms 的观察缺口清空旧轨迹；仍需至少 3 次匹配、面积增长 30%，再离场至少 150 ms 或明显缩小，才能形成待复核候选。过门只出现在 1–2 个输入帧、遮挡或角度差异仍可能漏检。旧版 v1 记录保留原规则；新版记录为 reference-motion-v2。

“导出本机诊断 JSON”包含累计计数和最近最多 120 次分析，不含图像；完整逐帧指标保留在本轮记录 JSON。所有诊断在本机产生，无远程埋点或画面上传。主机观察时刻仍不代表物理过门精度；采集卡延迟、曝光时间和视频与打杆偏移尚未校准。

真实模型链路可在隔离的本地服务执行，使用 Chromium 自带合成摄像头，获取真实模型资源，不接触用户采集卡或录像：

```bash
npm run dev -- --hostname 127.0.0.1 --port 3112
# 另一个终端；不要指向正在训练的服务
FPV_VISION_SMOKE_BROWSER=chromium node scripts/smoke-live-vision.mjs http://localhost:3112
```

脚本验证实际共享视频流、至少 8 帧真实 Worker 推理、实际后端/权重与诊断指标、本地保存与导出、无素材上传，以及停止识别后保留采集轨道。报告与截图写入已忽略的 `output/playwright/live-vision-smoke/`。脚本通过也不构成真实 FPV 穿越、正式计时或四路运行验收。

0.6.0 历史基线（2026-09-05）：开发服务与生产构建分别完成 8 帧真实模型推理。生产构建单帧约 274–299 ms，只有一次摄像头获取，停止后共享轨道仍在线，导出与本地保存一致；6 个外部资源 GET，没有网络写入、页面或 HTTP 错误。本次首次模型准备约 101 秒，明确记为未分析缺口；下载耗时依赖网络与缓存，不能据此承诺立即启动。

0.6.0 历史检查：592 项单元测试、Lint、生产构建和 22 项浏览器流程通过。随后强化实时流程并在该生产构建上通过定向复测：真实 MediaRecorder、打杆合成器与 OPFS 并行运行，停止计时后仍录制，视频实际字节与容器头、写入收据、训练 JSON 和实时记录关联一致。该流程仅模型协议使用确定性测试响应；另一个真实模型实验验证推理，两类证据均不替代实际采集卡与飞行验收。
